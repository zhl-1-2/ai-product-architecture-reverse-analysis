# 分阶段分析方法

## A. 用户旅程模式

先输出证据表，再输出三泳道旅程图。

证据表字段：阶段、用户目标、用户动作、页面反馈、用户需要做的决定、页面/数据/产物状态变化、问题或阻力、证据。

泳道仅保留：用户、产品界面、系统结果。必须包含：

- 正常主流程
- 用户修改/纠偏流程
- 失败与中断流程
- 菱形判断：接受/修改、成功/失败、继续/中断、权限或额度充足/不足
- 每个节点的证据编号
- 用户情绪、想法、痛点和产品机会点

## B. Agent 契约模式

不要预设 Agent 数量。按首次出现顺序识别名称、触发者、接替关系、下游交接、是否重入和缺席步骤。

每个 Agent 检查六类输入：

1. 用户当前输入
2. 用户长期信息
3. 项目全局上下文
4. 上游 Agent 输出
5. 平台公共资产/知识/规则
6. 工具或运行时结果

每张 I/O 契约卡包含：

1. 核心目标
2. 触发条件
3. 输入信息及来源类型
4. 可观察判断
5. 调用工具
6. 输出信息：用户回复、页面组件、结构化字段、领域产物、状态、下游任务或外部动作
7. 全局上下文读写：字段、方向、生产者、消费者、时机、证据等级、证据
8. 完成条件
9. 异常与重试
10. 尚未确认的问题

随后输出工具总表、全局字段表和生产者—消费者关系表。重点检查多版本、稳定引用、修改后失效、只写不读、只读不写、外部副作用，以及“口头完成但状态未更新”。

## C. 单 Agent Prompt 模式

先确认目标 Agent 的职责边界和全部出现记录，再编写“功能等价”而非“官方原文” Prompt。

分析内容：输入契约、输出契约、工具契约、状态机、事实/推断/建议规则、规则—证据追溯、最小测试集。

状态至少检查：`waiting_input`、`planning`、`waiting_confirm`、`executing`、`validating`、`completed`、`failed`、`interrupted`、`retrying`、`handoff`。仅保留证据或设计需要的状态。

功能等价 System Prompt 应覆盖：

1. Agent 名称与角色
2. 核心目标
3. 任务边界
4. 输入契约，区分必填与可选
5. 全局上下文协议，含允许读写、禁止修改、生产者、消费者和依赖失效
6. 工作流程与进入条件
7. 工具调用规范、幂等和重试
8. 用户确认机制
9. 结果验证
10. 修改与回退
11. 异常处理
12. 状态机
13. 下游交接
14. 完成条件
15. 结构化输出格式

最小测试集至少覆盖：输入完整、输入缺失、局部修改、工具失败、用户中断、页面与上下文冲突。每个测试写测试输入、初始状态、预期判断、工具调用、状态变化和禁止行为。

## D. 完整架构模式

完整架构同时还原五条流：用户交互流、Agent 控制流、工具调用流、数据/上下文流、领域产物与外部副作用流。

完整架构模式默认交付一份独立 HTML 报告。阶段性分析是报告内部章节，不应默认生成多份相互割裂的文件。必须按 [report-contract.md](report-contract.md) 将证据、结论、图表、源码、风险和未知项合并为一个可复核成品。

产品分层按证据选择组件，不强行填满：

1. 用户与渠道层
2. 交互与工作台层
3. 产品应用层
4. Agent 与流程编排层
5. 工具与服务层
6. 模型接入与路由层
7. 全局上下文与数据层
8. 知识与公共资产层
9. 基础设施与治理层

全局上下文应拆分领域对象，而不是画成一个大框。先使用通用主干，再按 [domain-profiles.md](domain-profiles.md) 增加领域对象。页面未出现的名称只能标记为推断或建议。

通用主干：

- UserContext：身份、偏好、语言、套餐、权限和长期记忆
- WorkspaceContext：组织、项目、会话、环境和协作者
- GoalContext：当前目标、要求、约束和成功标准
- DomainContext：领域输入、业务对象和中间状态
- ArtifactContext：代码、文档、数据、媒体、业务记录等产物及版本
- WorkflowState：当前 Agent、任务、确认、失败、中断和交接
- ToolExecutionContext：工具请求、执行结果、重试、幂等键和副作用
- ModelContext：模型能力、参数、路由、限制、成本和调用结果
- PolicyContext：权限、安全、合规、版权、隐私和审批规则
- BillingContext：套餐、额度、预估、冻结、消耗和退款
- EvaluationContext：自动校验、用户反馈、质量结果和失败原因

知识架构需区分：领域专业知识、模型能力知识、提示词或操作模板、安全/合规规则、计费规则、用户私有知识、组织知识、平台公共知识、项目临时数据、反馈与模型表现数据。

底层技术只先写“需要的能力”，再写“可能选型”和“推荐方案”。无法确认具体数据库、消息队列、云厂商或语言时说明原因。

核心数据实体采用通用分析模板，不冒充真实表名：User、Organization、Workspace、Project、Conversation、Agent、AgentRun、Workflow、Task、ToolCall、DomainObject、Artifact、ArtifactVersion、UserConfirmation、PermissionGrant、ModelInvocation、ExternalAction、Error、BillingRecord、Evaluation、Feedback。领域实体按产品类型追加。

## E. 横向检查清单

每种模式都要检查：

- 用户修改上游内容后，下游产物、缓存、索引或外部动作是否失效、撤销或局部重算
- 重试是否幂等，是否可能重复扣费、重复建产物、重复写库、重复部署或重复发送
- 套餐、额度或费用是否预估、冻结、结算和退款
- 用户中断是否传播到后台任务
- 工具成功但状态写入失败如何处理
- 数据对象和产物是否有稳定 ID、版本、来源与引用关系
- 结果质量是否按领域验证；例如代码需构建与测试，研究需来源与引用，数据需口径与可复现，业务动作需权限与回执，媒体需一致性与音画质量
- Agent 完成是否受系统完成门约束
- 用户私有数据、组织数据和平台公共知识是否隔离
- 模型能力、限制、安全与计费规则是否由服务强制执行，而非只依赖 Prompt
